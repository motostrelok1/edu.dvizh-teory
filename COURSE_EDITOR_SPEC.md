# COURSE_EDITOR_SPEC — Визуальный редактор учебного курса ДВИЖ

Статус: **ТЗ / планируется; реализация не начата**  
Дата: 2026-10-13  
Проект: `edu.dvizh-teory` / `https://edu.dvizh-school.ru`  
Связанные документы: [PROGRESS.md](PROGRESS.md), [SPEK_AUTH.md](SPEK_AUTH.md), [README.md](README.md)

## 1. Цель и границы

Создать защищённый визуальный редактор учебных материалов ПДД, доступный пользователям с соответствующими правами. Редактор должен позволять создавать, исправлять, дополнять, структурировать и публиковать страницы, изображения, межстраничные ссылки и тесты **без ручного редактирования исходного кода и JSON**. Курсанты видят только опубликованные редакции.

**Входит в MVP:** список разделов и страниц, редактирование и порядок блоков, загрузка и выбор картинок, настройка размера/позиции изображения, внутренние и внешние ссылки, предпросмотр, черновики и публикация, версии/откат, права и аудит.  
**Следующая очередь:** полноценный редактор тестов, совместная работа, медиаобработка/кроп, согласование публикаций, локализация.  
**Не входит:** произвольное исполнение HTML/JS, редактирование исходного PDF непосредственно в браузере, генерация юридически актуальных ПДД без проверки.

## 2. Исходное состояние и ключевые ограничения

- React 19, TypeScript, Vite, статический `public/sections.json`, иллюстрации в `public/img/`.
- Модель `src/types/pdd.ts`: `Section { id, title, blocks }`, блоки `p/h2/img/motivation/topic/lead/quote/term/example/quiz`. `ImgBlock { src,w,h }`.
- `src/components/LectureView.tsx` и `SectionView.tsx` ограничивают ширину изображения 90–330 px; нужно заменить на адаптивную модель размеров с сохранением пропорций.
- `src/lib/refs.ts` автоматически связывает упоминания знаков/разметки; обычных управляемых ссылок на разделы нет.
- `tools/make_all_lectures.py` перезаписывает блоки при генерации. **Ручные правки нельзя хранить там, где генератор их затрёт**.
- Серверного хранилища/ролей пока нет; см. `SPEK_AUTH.md`. Хранение прогресса в `localStorage` — отдельная задача.
- Структура ПДД содержит нормативные выдержки и авторские объяснения. Их режимы редактирования различаются.

## 3. Роли и права

| Операция | Гость/курсант | Редактор курса | Администратор |
|---|---|---|---|
| Читать опубликованную версию | Да | Да | Да |
| Читать и менять черновик | Нет | Да | Да |
| Загружать медиа, создавать страницы, ссылки | Нет | Да | Да |
| Публиковать и откатывать | Нет | По отдельному разрешению | Да |
| Менять роли, управлять удалением медиа | Нет | Нет | Да |
| Менять защищённые нормативные цитаты | Нет | Нет | Через управляемую процедуру и аудит |

Ролевые проверки выполняются **на сервере** на каждую операцию; скрытие кнопок в UI не считается защитой. Стартовый вариант допускает только роль «администратор» до внедрения дополнительных ролей.

## 4. Функции редактора

### 4.1. Навигация и структура
1. Дерево/список разделов; добавление, переименование, дублирование, перемещение и архивирование страниц.
2. Стабильные ID разделов и блоков, отдельные от заголовка/позиции; смена названия не ломает ссылки, прогресс и историю тестов.
3. Упорядочивание страниц/блоков мышью с доступными клавиатурными альтернативами и подтверждением опасных операций.
4. Поиск страниц и блоков по заголовку/содержимому; отображение статуса публикации.
5. Удаление страницы в MVP — **мягкое** (архив) с предупреждением о входящих ссылках.

### 4.2. Редактирование текста и блоков
1. Визуальное редактирование текста, заголовков, цитат, мотивации, объяснений, терминов, примеров/антипримеров, списков и иллюстраций.
2. Создание, вставка, копирование, дублирование, изменение типа, перемещение, удаление блоков.
3. Форматирование: абзацы, жирный/курсив, маркированный и нумерованный списки, ссылки. Допустимые форматы жёстко определены типизированной схемой; произвольный HTML запрещён.
4. Отмена/повтор, индикатор несохранённых правок, автосохранение черновика с защитой от потери данных.
5. Нормативные блоки `quote` по умолчанию read-only для редактора; администратор меняет их только с указанием источника/редакции и журналированием.

### 4.3. Изображения и медиабиблиотека
1. Загрузка PNG/JPEG/WebP (SVG допускается только после отдельного решения по безопасной обработке), проверка расширения, MIME, сигнатуры, размера и лимита файла на сервере.
2. Выбор ранее загруженного файла, замена изображения внутри блока, удаление блока без удаления исходного файла.
3. Параметры блока: ширина в % контейнера и ограничение `maxWidth`, выравнивание слева/по центру/справа, подпись, alt-текст, отступы, отображение на мобильных устройствах.
4. Пропорции сохраняются по умолчанию; ручная обрезка и варианты для устройств — после MVP.
5. Удаление физического файла запрещено, пока на него ссылается хотя бы одна опубликованная версия, черновик или сохранённая версия.
6. Пример минимальной модели: `{id,type:"img",assetId,widthPercent:70,maxWidthPx:720,align:"center",alt:"...",caption:"..."}`; пользовательские значения проверяются по схеме.

### 4.4. Ссылки и переходы
1. Вставка ссылки на страницу/раздел из списка с поиском; ссылка содержит целевой **ID**, необязательно отображаемый текст.
2. Ссылки на подраздел/якорь через стабильный ID блока, на знак/разметку по коду, на внешние HTTPS-адреса.
3. Предпросмотр и проверка ссылки перед публикацией: цель существует и опубликована, внешняя ссылка корректна.
4. Переименование/перемещение цели не меняет её ID; архивация/удаление показывает входящие зависимости.
5. Сохранить существующее автоматическое распознавание знаков/разметки; ручные ссылки имеют приоритет и не подвергаются повторному автопреобразованию.

### 4.5. Тесты
1. MVP: отображение и перенос существующих `quiz` без повреждения, режим чтения в редакторе.
2. Следующий этап: создание/удаление/порядок вопросов и вариантов, один правильный ответ (с возможностью последующего расширения), объяснение, проверка корректности и предпросмотр.
3. Каждому вопросу назначить стабильный ID и версию; опубликованные тесты неизменяемы в контексте сохранённой попытки. История попыток должна ссылаться на версию вопроса/публикации.
4. Аттестация с таймером/лимитом ошибок и назначением администратором — отдельный модуль, не смешивать с обычными проверочными тестами.

## 5. Черновики, версии и публикация

- У каждой страницы есть рабочий черновик и опубликованная версия. `Сохранить` не означает `Опубликовать`.
- `Предпросмотр` отображает черновик так, как его увидит курсант на desktop/mobile, но без публичного доступа.
- Публикация — атомарная операция: сначала валидировать структуру, обязательные поля, ссылки, ссылки на медиа и права, затем создать неизменяемую опубликованную ревизию.
- Сохранить автора, время, комментарий изменения, diff/номер ревизии и журнал действий; откат создаёт **новую ревизию** из старой, сохраняя историю.
- Не допускать «тихого» перезаписывания при параллельном редактировании: optimistic concurrency по `revision` с сообщением о конфликте.
- Курсанты продолжают читать ранее опубликованный вариант при ошибке сохранения/публикации.
- Массовые изменения и обновление нормативных материалов проходят предпросмотр различий и явное подтверждение.

## 6. Хранилище и API (проектное решение)

**Предлагаемый вариант:** Supabase PostgreSQL + Storage + серверные правила доступа. До реализации подтвердить, использовать ли отдельный Supabase-проект/схему или интеграцию с платформой автошколы. Разделение данных и ролей по умолчанию предпочтительно до решения о едином входе.

Рекомендуемые сущности:
- `courses`: id, title, status.
- `sections`: id, course_id, title, slug, sort_order, archived_at.
- `section_drafts`: section_id, content_json, revision, updated_by, updated_at.
- `section_revisions`: id, section_id, version, content_json, published_at, published_by, change_note.
- `section_publications`: section_id, current_revision_id (либо эквивалентный атомарный указатель).
- `media_assets`: id, storage_path, mime, width, height, checksum, alt_default, uploaded_by, created_at.
- `content_links`: source_section_id, source_block_id, target_type, target_id/code/url (возможно производная таблица индекса ссылок).
- `course_audit_log`: actor_id, action, entity_id, old_revision, new_revision, occurred_at.

Все блоки должны иметь устойчивый `id`; содержимое валидируется схемой до сохранения и публикации. Публичное чтение может использовать versioned JSON-снапшоты, чтобы сохранить быстрый статический клиент и уменьшить нагрузку на БД. Секреты и service-role ключи никогда не включать в браузерную сборку.

## 7. Совместимость и миграция

1. Создать резервную копию текущего `public/sections.json` и `public/img/`; записать контрольные суммы.
2. Разработать версионированную схему контента (`schemaVersion`) и конвертер текущих типов без изменения порядка блоков и существующих ID разделов.
3. Импортировать все 30 разделов и связанные изображения; проверить количество блоков, картинок, вопросов и разрешение ссылок до переключения чтения.
4. Генераторы Python переводятся в роль **импорта предложений/обновлений**, а не прямого перезаписывания опубликованного курса. Новые данные сравниваются с действующей редакцией и требуют подтверждения.
5. Обеспечить совместимость старых URL/hash и существующего прогресса `pdd-progress-v1`, пока миграция прогресса не будет реализована.
6. При недоступности редакторского API опубликованные страницы продолжают открываться из последнего корректного снапшота.
7. Отдельно проверить актуальность юридического текста ПДД перед публикацией нормативных обновлений.

## 8. Безопасность, доступность, эксплуатация

- HTTPS, серверная RBAC/RLS-проверка, аудит публикаций и удаления, запрет XSS/HTML-вставок, CSP, проверка URL-схем.
- Ограничения на размеры и частоту загрузок, обработка файлов без выполнения вложенного кода, безопасные имена объектов, резервные копии БД и медиа.
- Возможность работы клавиатурой, подсказки полям, обязательные alt-подписи для информативных схем.
- Автоматизированные unit-тесты схем и ссылок, интеграционные тесты прав/публикации, e2e основных редакторских сценариев. GitHub Actions: lint + typecheck/build + tests на PR.
- Удаление медиа/страницы только через проверку ссылок, подтверждение и журнал.
- Работоспособность предпросмотра на мобильном экране; не требовать редактирования с телефона в первой версии.

## 9. Критерии приёмки MVP

- [ ] Администратор может создать страницу, изменить заголовок, вставить/удалить текстовые блоки и переставить их без правки JSON.
- [ ] Можно вставить/заменить/убрать картинку, изменить её ширину и выравнивание; размер корректен на desktop и mobile.
- [ ] Можно создать внутреннюю ссылку выбором страницы/блока; переименование цели не ломает переход.
- [ ] Проверка перед публикацией обнаруживает битые внутренние ссылки и отсутствующие изображения.
- [ ] Сохранение черновика не меняет публичную версию; после публикации курсанты видят новую.
- [ ] Есть предпросмотр, история опубликованных ревизий и откат.
- [ ] Доступ к изменению/публикации закрыт для курсанта даже прямым API-запросом.
- [ ] Существующие 30 разделов, рисунки, тесты, ссылки на знаки/разметку и навигация работают после импорта.
- [ ] Перегенерация ПДД не перезаписывает ручные дополнения без явного согласования.
- [ ] Сборка, проверки схем, прав и публикации проходят в CI.

## 11. Решения перед началом разработки

1. Выбор хранилища: отдельный Supabase или общий с `driving-school`; единый вход — отдельное решение.
2. Кто может публиковать: только администратор или назначенный редактор.
3. Допустимые форматы/лимиты изображений и необходимость обрезки в первой очереди.
4. Порядок изменения нормативных цитат и указание редакции/источника.
5. Будут ли новые курсы помимо ПДД и нужна ли вложенная структура страниц с первого релиза.

**До согласования этих пунктов не начинать необратимую миграцию и не изменять работу действующего учебника.**
